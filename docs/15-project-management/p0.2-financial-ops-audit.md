**Status:** COMPLETE (audit only — no production code changes)  
**Date:** 2026-08-12  
**Scope:** Money-changing operations in Nexora POS after M6 GREEN  
**Verdict:** **YELLOW — HARDENING REQUIRED**

Canonical strategy: `STRATEGY.md`. Do not treat this as an implementation plan until CEO/CTO review.

## G. Final Verdict

### `YELLOW — HARDENING REQUIRED`

Core money paths (pay, refund, shift recon) are largely correct and tested. **No STOP-the-line defect that invents money or double-refunds** was found in the M6 refund path.

However, pilot financial truth is compromised by:

1. Reports that mix **gross tender** vs **net collected** after refunds  
2. **Re-payment allowed on `refunded` / `partially_refunded` bills**  
3. **Payments/discounts/order-cancel lack financial audit events**  
4. Optional payment idempotency (duplicate tender possible without key/`transaction_id`)

**Not RED:** refunds are atomic, PIN-gated, idempotent, recon-aware.  
**Not GREEN:** reporting + re-pay + payment audit gaps before “boringly reliable” pilots.

| P0-1 | **Re-payment on refunded bills** — `preparePaymentBatch` only rejects `payment_status === 'paid'`. After full refund, status=`refunded`, `paid_amount=0`, so a new payment can re-collect full total and append `payment_details` while sticky `shift_id` remains. | `bills.ts` ~551–553 |
| P0-2 | **Reports mix gross vs net** — `SUM(paid_amount)` is net; `paymentMethodBreakdown` sums original `payment_details` (gross, ignores refunds). `/sales` with `paidOnly` **drops** `partially_refunded`/`refunded` from method mix → undercount vs daily-stats overcount. | `reports.ts` ~109–131, 172+, 336 |
| P0-3 | **Payments unaudited** — highest-volume money mutation has no `logAuditEvent`. | `bills.ts` `applyPaymentBatch` |

## E. Recommended Changes (review gate — do not implement yet)

### E1. Block (or explicitly reopen) payment after refund — P0
- **Problem:** `refunded`/`partially_refunded` accepted for new payments.  
- **Evidence:** `bills.ts` ~551.  
- **Risk:** Re-collection + gross `payment_details` growth; sticky `shift_id`.  
- **Fix:** Reject pay unless status ∈ `{unpaid,partial}` OR add explicit `reopen` that clears policy.  
- **Files:** `bills.ts`, payment tests.  
- **Test:** pay after full refund → 409; partial refund remaining only.

### E2. Report gross vs net contract — P0
- **Problem:** Method totals ignore refunds; `/sales` paidOnly drops refunded statuses.  
- **Fix:** Document net = `paid_amount`; method mix = gross **or** net-by-method via refunds table; include refund statuses in sales filters appropriately.  
- **Files:** `reports.ts`, report tests.  
- **Test:** paid → refund → daily-stats / sales / methods assertions.

### E3. Audit `payment.received` inside payment txn — P0/P1
- **Problem:** No audit on money-in.  
- **Fix:** `logAuditEvent` in `applyPaymentBatch` with amount/method/bill/shift.  
- **Files:** `bills.ts`.  
- **Test:** audit row after pay.

### E4. Require payment Idempotency-Key (or txn_id for non-cash) — P1
- **Files:** `bills.ts`, POS PaymentModal (already sends keys — enforce server-side).  
- **Test:** missing key → 400; replay safe.

### E5. Order cancel + paid bill policy — P1
- **Fix:** Block cancel when any bill has net paid &gt; 0 unless refunded first; add `order.cancelled` audit.  
- **Files:** `orders.ts`.

### E6. Day-close refund fields — P1
- **Fix:** Add `cash_refund_total_cents` to summary; keep expected from persisted shifts.  
- **Files:** `day-close.ts`, day-close tests.

### E7. Loyalty credit type discrimination — P1
- **Fix:** `alreadyCredited` only for cashback description/type flag, not any credit.  
- **Files:** `bills.ts`.

### E8. topProducts exclude void_adjustment / cancelled — P1
- **Files:** `reports.ts`.

**Do not** change M6 refund architecture unless E1 reveals a deeper refund bug (none found in refund service itself).

## F. P0.3 Money Migration Plan (document only)

### Current
- REAL on orders/items/bills money columns; `payment_details.amount` dollars  
- INTEGER cents on shifts + `refunds.amount_cents`  
- In-memory `Math.round(x*100)` at payment/refund boundaries  
- Tax engine uses Decimal.js then stores REAL

### Target
- INTEGER minor units (cents) for all persisted money  
- Display conversion only at API/UI edge  
- Align loyalty points with explicit unit docs

### Strategy
1. Inventory all REAL money columns (orders, order_items, bills, products prices, refunds.amount)  
2. Additive columns `*_cents` OR migrate in place with dual-read period  
3. Write path: compute cents first; derive REAL for backward compat readers  
4. Backfill: `ROUND(real * 100)` with integrity report for 0.02 drift rows  
5. Cutover: readers prefer cents; drop REAL later

### Compatibility
- Export/import, cloud outbox, receipt printers, frontend MoneyDisplay  
- Upgrade-path tests from v72+ fixtures

### Rollback
- Keep REAL columns until dual-write proven; feature flag read preference

### Tests
- Fresh + upgrade DB; payment/refund/tax/discount golden amounts; recon unchanged; report fixtures

**Do not implement in P0.2.**

## Cash formula (approved, verified)

```
expected_cash_cents =
  opening_float_cents
  + qualifying cash applied on bills WHERE bills.shift_id = shift
  - completed cash refunds WHERE refunds.shift_id = shift
```

Card/wallet/custom refunds do **not** affect expected cash.

Missing cash-affecting ops: **no** till pay-in/out / cash adjustment entity.
