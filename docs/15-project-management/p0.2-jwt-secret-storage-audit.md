## 1. Executive summary

Today Nexora stores the JWT signing secret as **plaintext** in SQLite `settings.jwt_secret` (or optional `JWT_SECRET` env override). The secret is **256-bit** (`crypto.randomBytes(32)` → 64 hex chars), generated lazily on first auth use, and shared by POS / KDS / Server App **in one Electron Node process**.

**Highest practical risk:** full `.db` backups (local + Google Drive) contain the forge key. An attacker with a backup can mint owner JWTs forever until the secret is rotated—independent of password hashes. JSON export already redacts the secret; official restore **keeps the live install’s secret**.

**Recommended architecture (one):** reuse the existing Electron **`safeStorage`** pattern already used for Master PIN and Google Drive tokens:

- Ciphertext in `userData/jwt-secret.enc` (mode `0o600`)
- **Remove plaintext `jwt_secret` from SQLite**
- Keep `JWT_SECRET` env for CI/tests only
- Same-machine restore keeps `userData` ciphertext; cross-machine restore **regenerates** secret and forces re-login (fail-closed for forgery continuity)

Do **not** introduce keytar, cloud KMS, or microservices.

## 2. Current JWT lifecycle (code truth)

### 2.1 Secret creation

| Aspect | Behavior | Evidence |
|--------|----------|----------|
| Function | `getJWTSecret()` | `main/routes/auth.ts` |
| Entropy | `crypto.randomBytes(32)` → hex (256-bit) | Adequate |
| Timing | Lazy on first call when DB row missing | Not migration-seeded |
| Env override | `process.env.JWT_SECRET` wins; skips DB write | CI/tests |
| Regeneration | Only if cache cleared **and** DB row absent (e.g. factory reset) | Restart alone does not rotate |
| Failure | Throws if DB not ready | Fail-closed for auth |

Log line: `[Auth] Generated new JWT secret for this install` — **does not log the secret value**.

### 2.2 Storage & retrieval

```
JWT_SECRET env ──┐
                 ├─► in-memory _jwtSecret cache ─► jwt.sign / jwt.verify
settings.jwt_secret (plaintext SQLite) ──┘
```

- **Masked list API:** `GET /api/settings` returns `****` + **last 4 chars** to all staff roles (`SENSITIVE_SETTING_KEYS`).
- **Direct GET** `/api/settings/jwt_secret` → **403**.
- **IPC** `get-settings` same mask; write blocked.
- **JSON export** → `[REDACTED]`.
- **Full `.db` backup** → **includes plaintext secret**.

### 2.3 Signing / verification

| Site | Sign | Verify |
|------|------|--------|
| Main auth routes (login, refresh, setup, tenants) | Yes | Yes |
| Main `requireAuth` | No | Yes |
| KDS server login + middleware + WS | Yes | Yes |
| Server App login + middleware | Yes | Yes (also forwards Bearer to localhost POS) |

Algorithm: HS256 (jsonwebtoken default). TTL: `24h` or `10d` with rememberMe (KDS login always `24h`).

### 2.4 Refresh / revocation / staleness

| Mechanism | Reality |
|-----------|---------|
| Refresh tokens | **None.** `POST /api/auth/refresh` re-signs a new **access** JWT from the current access JWT. Frontend does **not** call refresh today. |
| Revocation | `sha256(full token)` → `revoked_tokens` (+ memory). **`jti` is minted but unused.** |
| Logout | Main + KDS persist revoke with exp; Server App logout may be memory-only if exp omitted. |
| `tokens_valid_after` | Password/PIN change, staff deactivate → reject tokens with earlier `iat`. Role always re-read from DB. |

### 2.5 First-run / reset / restore

| Event | Secret behavior |
|-------|-----------------|
| First run | Generated on first `getJWTSecret()` |
| Factory reset | New DB → new secret after cache clear |
| Official restore | **Live** `jwt_secret` preserved over backup (`RESTORE_PROTECTED_SETTING_KEYS`) |
| Raw file replace of `flo.db` | Backup secret applied as-is (bypass path) |

## 3. Process access map

All production HTTP servers run **in-process** with Electron main (shared SQLite + shared `_jwtSecret` cache). No secret distribution over LAN.

| Process | Needs signing secret? | Needs verification secret? | How currently gets it? |
|---------|----------------------|----------------------------|------------------------|
| Electron main | No | No | Starts servers; clears cache on restore/init; does not expose secret to renderer |
| POS Express (:3001) | **Yes** | **Yes** | `getJWTSecret()` |
| KDS (:3002) | **Yes** | **Yes** | Same |
| Server App (:3003) | **Yes** | **Yes** | Same; proxies Bearer only to `127.0.0.1:3001` |
| Frontend / renderer | No | No | Bearer token in `localStorage` only |
| Standalone KDS UI | No | No | Bearer only |
| Tests | Yes (fixtures) | Yes | Prefer `JWT_SECRET` env before import |
| `dev-server.js` | Indirect | Indirect | Same servers; may load `.env` |

**Design rule:** renderer, browser, LAN clients, and Settings APIs must **never** receive the signing secret (tighten last-4 leak as part of implementation).

Because sign and verify share one HS256 key in one process, splitting “verify-only” processes is **not required** for current architecture. Do not expose the secret via IPC to the renderer “for convenience.”

| Attacker obtains | Forge JWTs? | Impersonate owner? | Bypass RBAC? | Future tokens? | Revocation help? | DB encryption? | FS perms? | OS keychain / safeStorage? |
|------------------|-------------|--------------------|--------------|----------------|------------------|----------------|-----------|----------------------------|
| **A. SQLite DB** | **Yes** | **Yes** (mint owner JWT; role claim ignored—DB role used, but they can also edit DB) | Partially—can edit users table too | Yes | Revocation list is in same DB—attacker can clear it | Would raise bar if whole DB encrypted (out of scope) | Helps if other users can’t read file | **Moves forge key out of DB** ← goal |
| **B. SQLite backup** (local/Drive) | **Yes** (same as A) | Yes | Same | Yes | Same | Same | Same | **Exclude secret from backup** |
| **C. Install dir** | No (secret not in asar) | No | No | No | N/A | N/A | N/A | N/A |
| **D/E. Config / userData** | If `flo.db` or future `.enc` readable | Same | Same | Same | — | — | `0o600` helps multi-user | Protects ciphertext at rest vs casual copy |
| **F. Local FS read (same OS user)** | Yes if can read DB (or decrypt .enc as same user) | Yes | Yes | Yes | Limited | Limited | Weak vs same-user malware | **safeStorage binds to OS user/session—not malware running as that user** |
| **G. LAN access** | No (secret not on wire) | Only with stolen Bearer / guessed password | No without token | No | Token expiry/revoke | N/A | N/A | N/A |
| **H. Access token** | No | As that user until expiry/revoke/stale | Role from DB | No | Yes | N/A | N/A | N/A |
| **I. “Refresh token”** | N/A (none exist) | — | — | — | — | — | — | — |

**CTO note:** safeStorage / OSCrypt protects against **offline DB/backup theft** and **other OS users**. It does **not** stop malware running as the café POS OS user. That is acceptable for a local-first desktop POS; combine with staff-LAN (P0.1) and least-privilege OS accounts.

**Last-4 mask leak:** does not enable forgery of a 256-bit secret; still unnecessary disclosure → remove in implementation (P2 defense-in-depth).

## 7. Electron `safeStorage` — CTO assessment

From Electron docs / OSCrypt behavior:

- `isEncryptionAvailable()` is **false before `app.ready`**.
- macOS: Keychain service derived from **app name** (`"<AppName> Safe Storage"`)—renaming app can brick decrypt.
- Windows: DPAPI (user-scoped).
- Linux: gnome_libsecret / kwallet / basic_text.
- Encrypts strings to Buffer; app stores ciphertext on disk.

**Already proven in Nexora:** `master-pin.enc`, `google-drive-token.enc` with hard-block/throw when unavailable.

| Question | Answer |
|----------|--------|
| Protection? | OS-backed encryption of blob; not readable from Drive backup alone |
| Available before ready? | **No** — load secret **after** `app.whenReady` / after `initialize` starts (auth already after DB init in that path) |
| Packaged builds? | Yes (used today) |
| Headless Linux? | Often unavailable → must define fallback |
| Ciphertext in SQLite? | Possible but **worse for backups**; prefer `userData` file excluded from DB backup |
| Secret from local user/process? | Same OS user can decrypt—expected |
| Meets threat model? | **Yes for backup/DB exfiltration**; not for full OS-user compromise |

**Verdict:** safeStorage is the **right fit** for Nexora’s existing stack. Do not add keytar unless safeStorage proves insufficient on a supported pilot OS.

## 8. Architecture options

### OPTION A — OS keychain holds raw JWT secret (keytar-style)

- SQLite contains no secret.
- **Pros:** Classic pattern.  
- **Cons:** New native dependency, rebuild pain, Snap/MAS friction; duplicates what OSCrypt already does via safeStorage.  
- **Reject** for v1 hardening.

### OPTION B — safeStorage ciphertext in `userData` (RECOMMENDED)

- `userData/jwt-secret.enc` encrypted with `safeStorage.encryptString`.
- SQLite: delete `jwt_secret`; optional marker `jwt_secret_backend=safestorage`.
- `JWT_SECRET` env remains test/CI / headless escape hatch (never written to DB).
- **Pros:** Matches Master PIN/Drive; no new deps; removes secret from Drive backups; offline; single-process access unchanged.  
- **Cons:** Linux keyring / `basic_text` edge cases; app rename risk on macOS; must sequence after `app.ready`.

### OPTION C — Encrypted secret row still in SQLite

- Encrypt value with safeStorage before INSERT.  
- **Pros:** Single DB artifact.  
- **Cons:** Ciphertext still leaves on Drive; restore/merge complexity; little benefit over B.  
- **Reject** as primary.

### OPTION D — Keep SQLite plaintext + operational controls only

- Document “don’t upload DB offsite.”  
- **Reject** — Drive backup already uploads full DB; violates security requirements.

**Recommendation: OPTION B.**

## 9. Backup / restore strategy (design)

| Scenario | Expected behavior |
|----------|-------------------|
| **A. Restore DB → same machine** | `jwt-secret.enc` in `userData` untouched; auth continues; existing tokens still verify |
| **B. Restore DB → new machine** | No decryptable secret (or missing file) → **REGENERATE** new secret after explicit recovery path; all prior JWTs invalid; users re-login. Do **not** import plaintext from backup |
| **C. Other OS** | Same as B |
| **D. Other installation / fresh userData** | Same as B |
| **Google Drive / local `.db` backup** | Must **not** contain plaintext jwt_secret after migration. Do **not** upload `jwt-secret.enc` to Drive |
| **JSON export** | Remains redacted / omit |
| **Official restore merge** | Stop treating `jwt_secret` as SQLite protected key; protect **file** presence instead |

**Product rule:** Restoring business data must not silently restore forge capability to a new device.

## 12. Failure modes

| Case | Policy | Why |
|------|--------|-----|
| Keychain / safeStorage unavailable (desktop café) | **FAIL CLOSED** for auth after migration (clear error: secure storage required) | Avoid silent plaintext fallback undoing the control |
| Headless / CI | **RECOVER** via `JWT_SECRET` env | Tests already use this |
| Linux `basic_text` | **WARN + allow** or treat as degraded; document | Better than bricking; weaker than libsecret |
| Secret missing (no file, no env) | **REGENERATE** once + persist encrypted; force re-login | First-run / new machine |
| Corrupted `.enc` | **FAIL CLOSED** then operator recovery (regenerate with Master PIN) | Don’t silently mint a second live secret while old tokens still “expected” |
| Permission denied | **FAIL CLOSED** | Predictable |
| DB restored without secret file | **REGENERATE** (new machine semantics) | Tokens from old world invalid |
| Secret file without DB | Irrelevant; new DB generates/binds new secret | |
| Upgrade | Migrate plaintext → enc → delete row | Crash-safe steps below |
| Downgrade | Old build may recreate SQLite secret | Document: downgrade unsupported for security releases |
| Reinstall (same userData) | `.enc` may survive → tokens still work | OK |
| Reinstall (wiped userData) | **REGENERATE** | Re-login |
| Machine migration | **REGENERATE** | No silent secret copy in cloud backup |

**Critical rule:** Never silently generate a new secret **while leaving plaintext in SQLite** or while old forge key remains in Drive backups without operator awareness.

## 16. Migration design (crash-safe, not implemented)

```
OLD: settings.jwt_secret = plaintext
NEW: userData/jwt-secret.enc = safeStorage(ciphertext)
     settings: no jwt_secret row
```

### Phases

1. **Detect** — After `app.ready` + `initDatabase()`, if `settings.jwt_secret` present and no valid `.enc`, enter migrate.
2. **Import** — `encryptString(plaintext)` → write `jwt-secret.enc` (`0o600`).
3. **Verify** — Decrypt file; compare to plaintext; `jwt.sign`/`verify` smoke with cache.
4. **Remove plaintext** — DELETE settings row `jwt_secret` (txn). Optionally set `jwt_secret_migrated_at`.
5. **Normal startup** — Load only from `.enc` or `JWT_SECRET` env.

### Crash safety

| Crash point | Recovery |
|-------------|----------|
| After write `.enc`, before DELETE | Next boot: verify enc matches settings → DELETE (idempotent) |
| After DELETE, before cache warm | Load from `.enc` only |
| Enc write failed | **Keep plaintext**; log error; do not delete; retry next boot (FAIL CLOSED for “migration complete” flag) |
| Two secrets disagree | **FAIL CLOSED**; require owner recovery (Master PIN) → regenerate |

Never delete plaintext until decrypt verify succeeds.

### Existing tokens

Migration **keeps the same secret bytes** → existing JWTs remain valid (no mass logout). Rotation is a separate explicit action.
