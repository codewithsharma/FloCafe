## 1. Executive summary (discovery baseline)

Nexora POS intentionally runs **three cleartext HTTP servers**. Bind host is now **mode-dependent** (discovery found always `0.0.0.0` before this implementation):

| Service | Default port | Protocol |
|---------|-------------:|----------|
| Full POS API + static UI + KDS WebSocket | 3001 | HTTP + `ws://` |
| Standalone KDS (subset API + UI + WS) | 3002 | HTTP + `ws://` |
| Server App / waiter (subset; proxies to loopback 3001) | 3003 | HTTP |

The Electron shell talks to the backend over **`http://localhost:${getServerPort()}`**. LAN multi-device features remain first-class but require an **explicit** `network_mode`.

**Financial and destructive APIs require Bearer JWT + server-side role checks.**

**Approved model:** Model D + operational Model E (staff LAN). HTTPS (Model C) deferred.

**LAN SECURITY (post-implementation):**  
**GREEN WITH HARDENING**

### Startup sequence (code)

`main/index.ts` `initialize()`:

1. `initDatabase()`
2. `startServer()` → `:3001`
3. cloud sync / telemetry / Drive
4. `startKdsServer()` → `:3002`
5. `startServerApp()` → `:3003`
6. WhatsApp, **mDNS**, printers, IPC
7. `createWindow()` → `loadURL(http://localhost:${PORT})`

Same trio started by `dev-server.js` (backend-only). Packaged app uses the same embedded HTTP model (static UI from `resources/frontend-out`), not a remote API host.

### Bind configuration

- **Host:** hardcoded `'0.0.0.0'` — **not** env-configurable (`HOST` / `BIND` absent).
- **Ports:** `PORT` (3001), `KDS_PORT` (3002), `SERVER_APP_PORT` (3003).
- **TLS:** none for local listeners (`https.createServer` not used for POS/KDS/Server App).
- **EADDRINUSE:** each server retries up to 10 times, incrementing port.

### Client URL derivation

- Frontend axios `baseURL = window.location.origin + '/api'` — LAN IP origins work by design (`frontend/src/lib/api.ts`).
- Electron origin is localhost; LAN browser POS gets a different origin-scoped `flo_terminal_id`.

## 4. Threat model

**Assumptions in code today**

- Single-tenant café machine; API not meant for the public internet (`SECURITY.md`).
- LAN clients (second POS, KDS, waiter) are intentional.
- CORS is a browser convenience allowlist for private IPs — **not** a security boundary.
- `X-Flo-Terminal-Id` is **identification**, not authentication.
- Operators may place the POS host on the same Wi‑Fi as customers unless guided otherwise.

**Assets**

- JWT Bearer tokens (localStorage + Authorization header)
- Payment / refund / shift / day-close APIs
- Order create/void/status
- Staff credentials (login over HTTP)
- SQLite business data (via authenticated APIs; secret storage is Phase 2)
- Kitchen ticket stream (WS)

**Attacker positions**

1. Guest Wi‑Fi device on same SSID as POS  
2. Employee personal device on staff LAN  
3. Customer laptop (if guest = staff network)  
4. Compromised POS terminal (host already trusted)  
5. Malicious LAN client / scripted API caller  
6. Rogue KDS client  
7. Passive network sniffer (cleartext)  
8. Active MITM on open/WPA-personal café Wi‑Fi

## 7. Security gaps

1. **Hardcoded `0.0.0.0` on all three servers** — Electron-only cafés still expose full financial API to the LAN.  
2. **Cleartext HTTP/WS** — Bearer JWTs and payment/refund bodies sniffable on shared Wi‑Fi.  
3. **Full POS API on LAN by default** even when only KDS tablets are needed (3002 would suffice for kitchen-only).  
4. **Product advertises cleartext LAN URLs** (`pos-info`, `kds-info`, mDNS, Settings QR).  
5. **General rate limit bypass for private IPs** — DoS / abuse easier from LAN after auth.  
6. **No operator deployment mode** in code (localhost-only vs LAN-POS vs KDS-only).  
7. **Doc/operator gap** — prior SEC-01 called MEDIUM; café guest Wi‑Fi makes impact higher without a written trust boundary.  
8. **CORS treated as safety** in older narratives — it is not; native clients and stolen JWTs bypass it.  
9. **Public discovery surfaces** — health, setup status, static login UI, Bonjour.  
10. **Phase 2 adjacency** — `jwt_secret` in SQLite amplifies token forgery if DB/backup leaks (tracked separately; not fixed here).

| Finding | Severity | Rationale |
|---------|----------|-----------|
| Cleartext financial API on `0.0.0.0` when POS shares guest/untrusted Wi‑Fi | **P0** | Stolen JWT ⇒ payments/refunds/orders as that role |
| Same exposure on documented **staff-only** trusted LAN | **P1** | Still sniffable; smaller attacker set; acceptable short-term with operator controls |

Do not treat “auth exists” as GREEN. Do not treat “not on the public internet” as sufficient for guest Wi‑Fi cafés.

## 9. Recommended deployment model

### What the product actually requires (from code)

| Need | Required? |
|------|-----------|
| A. Localhost-only backend for Electron alone | **Sufficient for Electron window** — already uses localhost |
| B. LAN-accessible full POS API | **Required only if** browser/LAN second cashier (pos-info QR) is used |
| C. LAN-accessible KDS | **Required for** standalone kitchen tablets (`:3002`) |
| D. LAN-accessible Server App | **Required for** waiter tablets (`:3003`) |
| E. LAN inbound for printers | **No** — POS connects outbound to printer |

**Current shipped behavior = Model B (LAN HTTP)** with intentional multi-device clients.

### Recommendation (no product redesign)

**Adopt: Model D + operational Model E (hybrid), with Model B only when LAN POS is explicitly needed.**

| Layer | Policy |
|-------|--------|
| **Network (E)** | POS host on **staff-only SSID/VLAN**. Never guest Wi‑Fi. Document as mandatory for pilots. |
| **Bind (D path)** | Implement configurable listen modes (Phase 1.1 — after CEO/CTO approval): Electron-only → `127.0.0.1` for 3001/3003; KDS-only LAN → `0.0.0.0` on 3002 only; Multi-POS → `0.0.0.0` on 3001 with staff LAN. |
| **TLS (C)** | **Defer** to P2 unless pilots cannot provide network segregation. Café cert UX is poor without MDM. |
| **Auth** | Keep JWT + RBAC mandatory; never treat CORS as auth. |
| **Cloud** | None required — offline SQLite preserved. |

This preserves: offline POS, SQLite, KDS, LAN printing (outbound), scanners, terminal identity, Electron packaging, Win/macOS/Linux, optional LAN clients when operators choose them.

## 10. Alternatives considered

| Model | Fit to current architecture | Verdict |
|-------|----------------------------|---------|
| **A — Localhost only** | Breaks LAN POS, LAN KDS QR, Server App tablets, mDNS pairing | **Reject as sole model** — viable as an **operator mode** for Electron-only shops |
| **B — LAN HTTP (status quo)** | Exact current code | **Accept only behind staff LAN**; unsafe default on guest Wi‑Fi |
| **C — LAN HTTPS** | Would fix sniffing; needs cert trust on tablets (private CA / pinned) | **Defer (P2)** — high friction; keep design spike ready |
| **D — Localhost POS + LAN KDS only** | Matches kitchen-only deployments; Server App can stay LAN with loopback proxy | **Preferred technical hardening path** for shops without second cashier |
| **E — VPN / private network boundary** | Tailscale already in CORS allowlist (`100.64/10`); no VPN code required | **Required operational control for pilots** even before code changes |

Rejected: public-internet exposure, cloud-dependent auth gateway, reverse-proxy mandate for v1 pilots, redesigning away KDS/LAN POS.

## 13. Operator deployment guidance (draft for pilots)

**Supported**

1. POS PC on **staff-only** Wi‑Fi/VLAN (no guest devices).  
2. Kitchen tablets on same staff network → `http://<pos-ip>:3002`.  
3. Optional second cashier → same staff network → `:3001` QR.  
4. Optional waiter Server App → `:3003`.  
5. Network printers reachable **from POS** (outbound).  
6. OS firewall: deny inbound from guest VLAN; allow staff → 3001/3002/3003 as needed.

**Not supported / not production-safe**

- POS API reachable from café **guest** Wi‑Fi.  
- Open/public hotspot without segregation.  
- Port-forwarding POS ports to the internet.  
- Treating CORS or “private IP” as encryption.

**Until bind modes ship:** assume all three ports are LAN-reachable whenever the host is on that network — control exposure with **network design**, not application toggles.
