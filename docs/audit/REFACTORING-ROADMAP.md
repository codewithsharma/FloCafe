# Refactoring Roadmap — OPERAVIA (FloCafe)

**Date:** 2026-08-21 · **Version:** 3.0.5

A sequenced, evidence-driven plan across four horizons. Ordering optimizes **risk reduction per unit of effort** and respects the project's own constraints: the data-safety mandate (new migration version, preserve data, test fresh + upgrade, maintainer review), the R4.1 architecture-governance rule, Restaurant-only active development, and "keep the diff focused / reuse established patterns."

> Guiding principle: **do the cheap, high-leverage consistency work and safety-net wiring first**, because it also _de-risks_ everything after it. Every item below adopts a pattern that already exists in the codebase — this is convergence, not invention. Nothing here requires re-architecture.

Each item lists **effort** (S ≤1d · M ≤1w · L ≤1mo · XL >1mo), the **risks it retires** (from [RISK-REGISTER.md](RISK-REGISTER.md)), the **debt theme** (from [TECHNICAL-DEBT.md](TECHNICAL-DEBT.md)), and a **verification** step matched to the change.

## Cross-horizon guardrails

- **Data-safety gate (blocking):** any schema change (items 24, 25, 28) requires a **new migration version, data preservation, fresh + upgrade-path tests, and maintainer review** — no exceptions, per `AGENTS.md`.
- **R4.1 gate:** items touching `db.ts`, `routes/orders/*`, or the Settings page must _extract a boundary_, not grow the file. The `*-boundary` guards (wired in H1) enforce this once in CI.
- **Focused diffs:** each numbered item is independently shippable and reviewable; do not batch the money cutover with unrelated refactors.
- **Re-score after each horizon** against the weighted rubric in [CTO-ASSESSMENT.md](CTO-ASSESSMENT.md); H1+H2 alone should move Testing and DevOps materially.

## Sequencing rationale (why this order)

1. **H1 first** because wiring the orphaned recovery/boundary tests and gating the unit layer _retires the two testing High risks cheaply_ and creates the safety net that makes every later refactor verifiable.
2. **H2** converts the good-but-bypassed abstractions to defaults (logger, error handling, axios, headers) and unblocks signed distribution — user-facing trust with low code risk.
3. **H3** builds the real frontend + concurrency coverage that H4's money cutover will lean on, and takes the first (lower-risk) god-file split.
4. **H4** does the one XL, highest-risk change (money cents + payments table + FKs/CHECKs) **last**, on top of the coverage built earlier — the safest possible sequence for a financial migration.
